# Research flow: a slice:research stage and a research pipeline

## Goal

Slicewright runs features, not research: no stage answers questions from sources with evidence, and the stages that come close fight it as protocol. This slice adds one internal stage, `slice:research`, that takes research questions from the slice's spec, has research agents answer them from sources with cited evidence and a confidence, merges the findings into `research.md` with conclusions, options, a recommendation and follow-ups, and has review agents check it. Everything else is configuration in this repo: a research pipeline in `.slicewright/research.json` that agrees the questions with a person, runs the research, agrees the results, files the follow-ups the person chose as issues, and publishes a research page and, when a decision was reached, a decision record. For the people who develop Slicewright, a research topic then goes through the same gates and leaves the same records as a feature, and later slices start from what it found.

## Scope

**Changes:**

- `plugins/slice/skills/research/SKILL.md` (new): the research stage
- `plugins/slice/skills/run/SKILL.md`: `Skill(slice:research)` in `allowed-tools`, and the **Continue** choice of `new` mode switches to the configuration `status.md` records
- `plugins/slice/skills/configure/SKILL.md`: the `--config <name>` option, so that the command sets up another pipeline's permission rules
- `.slicewright/research.json` (new): the research pipeline
- `.claude/settings.json`: the permission rules the research pipeline needs
- `start-slice.sh`: the `--config <name>` option and the leftover slice's configuration in its note
- `tests/static.sh`, with `tests/static/` as needed, and `tests/selftest.sh`: a check of the project's configurations, and its self-test case
- `README.md` and `AGENTS.md`
- the documentation, staged in `slice/docs/`: `overview/structure.md` and `overview/testing.md`

**Out of scope:**

- `plugins/slice/defaults.json`: the research stage isn't in the default pipeline, and `research.json` isn't shipped with the plugin
- `.slicewright/config.json`: the default pipeline of this repo is unchanged
- a smoke test of the research pipeline: the hand run in AC11 is its only end-to-end check
- every other skill, and everything under `.slicewright/stable/`
- a research page's later life: who updates it when it goes stale

## Requirements

- **R1** A new internal skill, `plugins/slice/skills/research/SKILL.md`, with `name: research`, a description and `user-invocable: false`. Its arguments are a JSON object, and it uses only `activeSlicePath`, `knowledge`, `context`, `researchAgents` and `reviewAgents`, ignoring any other key. `researchAgents` and `reviewAgents` are lists whose entries have the agent format of every other stage: `executionMode` (`fork` or `inline`), `skill` or `agent` (`general-purpose` when neither is given), `context` and an optional `name`. Each `researchAgents` entry is one angle or one kind of source, and its `context` says which. When `researchAgents` is missing, the stage researches everything itself. When `reviewAgents` is missing, it uses one general-purpose reviewer; when it is an empty list, it skips the review. The stage never asks the person anything, never writes code, and changes no file but `<activeSlicePath>/research.md` and `<activeSlicePath>/design-reviews.md`. It follows the skill conventions in `AGENTS.md`: one command per call, no `cd`, files written with the Write or Edit tool, no version control named in the skill text, plain English.
- **R2** The stage reads `<activeSlicePath>/spec.md`, which holds the research questions as its requirements, the scope with the sources in and out, and under each acceptance criterion what a good answer to its question contains. Without `spec.md` it returns `NO_SPEC`. When `spec.md` still has an open question marked as blocking design, it returns `SPEC_NOT_READY`, naming the question. It also reads `<activeSlicePath>/input.md`, and `<activeSlicePath>/research.md` when one exists from an earlier run (R5).
- **R3** Before the agents start, the stage gathers the project's own knowledge once, into a brief: the project's documentation as `knowledge` describes it, read only where it bears on the questions, with staged pages in `<activeSlicePath>/docs/` read instead of published ones; the sources the stage's `context` names, such as the code or the records of earlier slices; and the rules of evidence and citation from the stage's `context` and from the spec's Constraints. Then it starts every `fork` research agent at once, in parallel, with one prompt that carries the entry's context, the paths of `spec.md` and `input.md`, the brief, and the answer form; it plays each `inline` entry itself. An agent answers with findings per question: for each question of the spec, each finding as the claim, its source cited as the rules say, and its confidence; where its sources disagree, the disagreement; and "nothing found" for a question its angle doesn't answer. Confidence is one of `low`, `medium`, `high` or `sure`, defined in the skill: `low` is inferred, or from a secondary source, or disputed; `medium` is stated by one source the agent read; `high` is stated by two independent sources, or by the primary source for the matter; `sure` is shown by the project's own code or documentation, or checked by the agent itself. An agent never changes a file and never asks the person anything. An agent that fails, or answers without the form, is started once more; when it fails again, the stage covers its angle itself and says so in the result.
- **R4** The stage merges the findings into `<activeSlicePath>/research.md`, in this order, leaving out the header line `slice:` when `input.md` has no id, and the sections that would be empty, except Questions, Conclusions and Recommendation:
  1. a header with `slice: <id>`, then the title `# Research: <the slice's title, as input.md gives it>`
  2. `## Questions`: one `### R<n> <question>` per requirement of the spec, in the spec's order, with **Answer** (the answer, or "not answered" with why), **Evidence** (each claim with its source and its confidence; a claim without a source is not evidence and isn't written), and **Disagreements** (where sources differ, which one the answer follows and why; or "none")
  3. `## Conclusions`: what the answers mean together
  4. `## Options`: one `### O<n> <option>` per course of action the conclusions allow, each with its trade-offs, for and against
  5. `## Recommendation`: one option and why, ending with the line `Decision:` left empty for the person
  6. `## Decisions`: the answers a person gave to open questions at a review, one line each, `- <the question>: <the answer>`. The stage never writes this section itself: it keeps it as it is, and treats each line as settled.
  7. `## Assumptions`: each assumption with why it holds, such as a source that couldn't be reached
  8. `## Open questions`: each `Q<n>` with why it matters, lettered options, the recommended answer the draft applies, and what it affects, as in `spec.md` and `design.md`
  9. `## Follow-ups`: one `- **F<n>** <what, and why it matters>` per piece of later work, each ending with `Decision:` left empty for the person
  10. `## Review notes`: only when a person left notes (R5); the stage removes the notes it has applied
- **R5** On a later run, the stage keeps what a person wrote in the earlier `research.md`: the lines under Decisions count as settled and are never asked again, filled `Decision:` lines stay as they are, and each note under Review notes is reworked and then removed. Answers to questions that the current `spec.md` still asks are kept unless a note asks to redo them; questions the spec no longer asks are dropped, and new questions are researched.
- **R6** The review runs the way it does in the clarify and design stages: every `fork` review agent starts at once, with a prompt that carries only the full spec, the full draft and the answer form (`Status: Approved | Issues found`, `Issues`, `Recommendations`); the stage plays each `inline` entry itself. Each issue is checked against the spec, the sources and the draft, then fixed or rejected with a reason; a recommendation that clearly improves the draft without widening it is applied, and the rest become open questions; contradicting reviewers are decided with a reason or become an open question; a reviewer that fails or answers without the form is started once more, and then counts as not run. Only when the stage has no tool for starting subagents does it review the draft itself and record that the reviews didn't run.
- **R7** The stage writes `research.md` with the Write tool, replacing the earlier version, and returns `WRITE_FAILED` when that fails. It appends the review record to `<activeSlicePath>/design-reviews.md`, creating it with the heading `# Design reviews` when missing, under `## research, <time>`, in the form clarify and design use. Its result block follows `skills/run/SKILL.md`, section 4.3: on success `result: ok`, a one-sentence message with the number of questions answered, the open questions, the follow-ups and any angle the stage had to cover itself, and `files` naming both files; on failure `result: error` with `code` one of `NO_SPEC`, `SPEC_NOT_READY`, `WRITE_FAILED`, a message, a fix and the files it changed.
- **R8** The runner, `plugins/slice/skills/run/SKILL.md`: `Skill(slice:research)` joins its `allowed-tools`. In `new` mode, when `/slice:new` was run without `--config` and the person chooses **Continue** for the slice in progress, the runner loads the configuration that `status.md` records, when it records one, checks its pipeline as in its section 2, says so, and continues the slice with it, as `resume` does. With `--config` given, the given configuration is used, as today. **Start new** is unchanged.
- **R9** `.claude/settings.json` allows `Skill(slice:research)`, and the `gh issue` commands the research pipeline runs, in `file-issues` and in intake: `Bash(gh issue create:*)`, `Bash(gh issue list:*)` and `Bash(gh issue view:*)`. Nothing else in the file changes.
- **R10** `.slicewright/research.json` holds the research pipeline, loaded with `/slice:new --config research`. It has `pipeline` and, only where it must differ from the defaults, `sharedParams`; `activeSlicePath` stays `./slice`. It passes the runner's own check (its section 2). Its stages, in order:
  1. `intake`: `slice:intake`, `fork`, with the same context as `config.json`'s intake stage.
  2. `clarify`: `slice:clarify`, `fork`. Its context says how a research topic fills the spec template: the requirements are the research questions, one each, concrete enough that an answer can be judged; each acceptance criterion says what a good answer to its question contains, the evidence it needs, and when it is good enough; the scope lists the areas the topic covers, and the sources in and out; the constraints hold the rules of evidence for this topic; follow-up slices are later research. Its one review agent checks the questions: each has what a good answer contains, the scope covers them, none is answered by the project's documentation or code already, none is two questions, and every open question has a recommended answer.
  3. `questions-review`: `slice:human`, `inline`, `files: ["spec.md", "input.md"]`, no `choices`. Its context presents the questions, the scope, the sources and what a good answer contains, with a summary of clarify's latest entry in `design-reviews.md`; walks the person through the open questions and the assumptions; applies the answers to `spec.md`, keeping its format and removing answered questions; the person decides whether to approve; on approval it appends a `## Session summary` to `input.md`, as `config.json`'s spec-review does.
  4. `research`: `slice:research`, `fork`, `onError: results-review`. Its context names the sources of the project's own knowledge beyond the documentation (the code, and the slice records in `.slicewright/slices/`), the order of trust between kinds of sources, how to cite (a link for a page, with the date read; a path for a file in the project), and what counts as evidence. Its `researchAgents`: `web`, a `general-purpose` agent that searches the web and reads primary sources; and `claude-code`, a `claude-code-guide` agent for anything about Claude Code, its plugins, skills, agents and the Claude API. Its one review agent checks `research.md` for: an answer without evidence, or a claim whose cited source doesn't say it (the reviewer opens the source); a source the spec rules out, or a question of the spec with no answer; evidence that disagrees without the disagreement noted; a confidence the evidence doesn't justify; an option without trade-offs; a recommendation that doesn't follow from the conclusions; an open question without a recommended answer.
  5. `results-review`: `slice:human`, `inline`, `files: ["research.md", "input.md"]`, `choices: {"accept": "file-issues", "more-research": "research", "re-scope": "clarify", "drop": null}`. Its context: when `research.md` is missing because research failed, present the failure recorded in `status.md`, say that accept needs a finished research, and say that a failure in the spec itself, `NO_SPEC` or `SPEC_NOT_READY`, is fixed through `re-scope`, not `more-research`. Otherwise present `research.md` in its own words: each answer with its confidence, the conclusions, the options, the recommendation, the follow-ups, and a summary of research's latest entry in `design-reviews.md`. Walk the person through the open questions; for each answered one, apply the answer in `research.md`, keeping its format, remove the question from Open questions, and add its question and answer as one line under `## Decisions`. Ask for the decision on the recommendation and write it on its `Decision:` line, as the decision in the person's words, or `none: <why>`. For each follow-up, ask on its own whether to file it as an issue, and write `Decision: file` or `Decision: no issue`. Then the choices: `accept`, only when the recommendation and every follow-up have a decision; `more-research`, after writing each of the person's requests as a note under `## Review notes` in `research.md`, naming the question or section it concerns; `re-scope`, after appending a `## Re-scope` section to `input.md` with the person's reasons and the new direction, never changing the text above it; `drop` ends the run.
  6. `file-issues`: `slice:deploy`, `fork`. Its context: for each follow-up in `research.md` with `Decision: file`, look for an open or closed issue of this repository with the same title with `gh issue list`, and when there is none create one with `gh issue create`: the follow-up's title, and a body with its text, why it matters, and where it comes from (the slice's title and, when `input.md` has one, its source issue). The target is this repository on GitHub, the endpoint is the list of issue URLs, created or found, each with its follow-up's id, and the check is `gh issue view` on each. With no follow-up marked `file`, the stage records that there was nothing to file and returns `ok`.
  7. `consolidate`: `slice:consolidate`, `fork`, `archivePath: "./.slicewright/slices"`, with three knowledge agents: `research` writes the research page `architecture/research/<name>.md`, where `<name>` is the slice's title from `status.md` in lowercase words joined with `-`, the way consolidate names a records folder when the slice has no id, so that a later consolidation finds the same page; its frontmatter has `type: research`, the date and the source issue when there is one; it holds the questions with their answers, evidence and confidence, the disagreements, the conclusions, the options, the recommendation with the decision taken, the decisions from the reviews, the open questions, and the follow-ups each with its issue from `deployments.md` or "not filed", and the agent updates the page when it exists from an earlier consolidation; `adr` writes one decision record in `architecture/decisions/` when the recommendation's `Decision:` line is neither empty nor `none`, numbered after the last, with the context from the conclusions, the decision, the other options as the alternatives with why each lost, the consequences, and a link to the research page, and marks a record the decision replaces as superseded; `index`, with `config.json`'s `index` context plus one rule, that a folder whose `index.md` is new is listed under Contents in its parent folder's `index.md`, so that `architecture/research/index.md` lists the page, `architecture/index.md` lists the folder, and `log.md` gets the slice's entry.
  8. `release`: `slice:deploy`, `fork`, with the same context as `config.json`'s release stage: push the branch and open or update the pull request.

## Constraints

- The skill follows the design rules and skill conventions in `AGENTS.md`: it holds the protocol and the template; the sources, the rules of evidence, the citation form, what is published and whether issues are filed stay in `research.json`. No new top-level configuration key: the research stage's settings are its params, and only the five R1 names.
- The research stage's `researchAgents` and `reviewAgents` use the agent entry format of every other stage, so the README's description of agents stays true.
- `plugins/slice/defaults.json` doesn't change. The research stage's params are documented in the skill and the README, not in `defaults.json`.
- `.slicewright/research.json` is loaded instead of `config.json`, not on top of it, so it repeats what it needs from `config.json`: intake's and release's contexts. This duplication is a consequence of how `--config` works, and the README says so.
- The scripts keep the rules in `architecture/concepts.md`: POSIX `sh` only, `dash -n` clean, exit 0, 1 or 2, one source per value, and a `FAIL` line that names its subject.
- `start-slice.sh` never runs from an agent. Its new option is checked by hand.
- The default pipeline's behavior doesn't change: `tests/smoke.sh` and `tests/smoke/` are untouched.
- Nothing under `.slicewright/stable/` changes.
- The research stage never changes the project's documentation: the research page and the decision record are consolidate's work, from `research.md` and `deployments.md`.
- The research pipeline always has a person at its gates, so it never runs headless.

## Assumptions

- One slice, not several: the script option, the runner fix and the documentation are each needed for the research flow to run end to end, and the issue scoped them together with the static check. If the slice turns out too large, R12, the static check, is the natural cut: the flow runs without it. The issue's out-of-scope list is kept as it is.
- The research page lives at `architecture/research/<topic>.md`: the issue gives that path as its example, and the architecture folder already holds the decision records that research feeds. Later slices find it through `architecture/index.md` and the folder's `index.md`, which the `index` agent keeps, so the documentation source's `context` in the configurations isn't changed.
- The research stage records its review in `design-reviews.md`, the file clarify and design share, because clarify writes it in the research pipeline anyway and one file keeps every document review of a slice together.
- The confidence scale is defined in the skill, as the diagnose skill defines its levels, so that every project's findings use the same words; what counts as a credible source and how to cite stay in the context.
- `SPEC_NOT_READY` mirrors the design stage: a blocking question left open at `questions-review` would otherwise be researched on a guess.
- The two research agents, `web` and `claude-code`, are this repo's choice: its research topics are about delivery pipelines and Claude Code. A project changes them in `research.json`. The `claude-code-guide` agent type exists in Claude Code on this machine.
- `start-slice.sh` checks only the project's `.slicewright/<name>.json`, as the issue says, although the runner also accepts a configuration that exists only in `~/.slicewright/`. The research pipeline is this repo's, so the project file is the one that matters.
- The rules of R9 are added to `.claude/settings.json` in this slice, so that the hand run of AC11 doesn't stop at prompts. `/slice:configure --config research --permissions` (R14) proposes the same rules, from its existing rule for every stage's skill and for the commands a `slice:deploy` context names, so a pipeline added later gets its rules from the command.
- The `gh issue` rules are added with the skill rule, so that `file-issues` and intake don't stop at prompts; the issue asked only for the skill rule, and the extra three lines are the commands the pipeline runs.
- The hand run's topic is the person's choice, and the run costs what a feature slice costs; neither is bounded here.
- Issues are filed before consolidate, so the research page and the archived records carry the issue numbers, and the issues name the slice and its source issue rather than a page that isn't merged yet.
- The research pipeline ends with a `release` stage, the same as `config.json`'s, because consolidate commits the research page on the slice's branch and this repo publishes through pull requests.
- The static check covers every `.slicewright/<name>.json` except `*.local.json`, so `config.json` as well as `research.json`, because the check is the same for both and one rule covers any pipeline added later.
